# 型とオプショナル { #types-optionals }

Wick は**型推論を備えた静的型付け言語**です。すべての式はコンパイル時に型が決まります。
型注釈が必要なのは、推論の手掛かりがない場合だけです。

## 型の一覧 { #the-types }

| 型 | 値 | 補足 |
|---|---|---|
| `num` | IEEE-754 倍精度 | Lua と同様、数値型はこれだけです |
| `bool` | `true`、`false` | 条件式に使える唯一の型です |
| `str` | 不変のテキスト | `+` で連結できるのは str+str のみです |
| `list<T>` | 順序あり、0 始まり | `T` は `num`、`bool`、`str`、または**レコード**です |
| `map<T>` | 文字列キー | 値は `num`、`bool`、または `str` です |
| *レコード* | 名前付きフィールド | [レコード](records.md)を参照してください |
| `T?` | `T` または `nil` | **オプショナル**。この言語の中心的な機能です |

`nil` は汎用の値ではなく、オプショナルだけが保持できます。`let x = nil` は、
型注釈（`let x: str? = nil`）がなければコンパイルできません。

## オプショナル: nil 安全性を強制する { #optionals-nil-safety-enforced }

失敗する可能性がある操作はオプショナルを返します。コンパイラは、
`nil` の場合に対処するまで、その値を利用することを許しません。

```wick
let s = lt.load_save("hi")     // s: str?
lt.print(s, 4, 4, 1, 1, 1, 1)  // COMPILE ERROR: str? where str expected
```

対処方法は 2 つあります。

**1. `??` — 既定値を指定してアンラップする**

```wick
let text = s ?? "no save yet"        // text: str
let n = num("maybe") ?? 0            // num() parses str -> num?
```

`??` は左辺が `nil` の場合にだけ右辺を評価し、
結果の型はオプショナルではない元の型になります。

**2. 型の絞り込み — `if x != nil`**

```wick
if s != nil {
  // inside this block, s: str (narrowed)
  lt.print(s, 4, 4, 1, 1, 1, 1)
}
```

型の絞り込みが使えるのは**ローカル**変数です。モジュールのグローバル変数には `??` を使ってください。
ブロック内で新たなオプショナル値を代入すると、絞り込みは解除されます。

## オプショナルを返す式 { #what-returns-an-optional }

| 式 | 型 | `nil` になる場合 |
|---|---|---|
| `lt.load_save(k)` | `str?` | 読み取れるセーブデータがない |
| `num(s)` | `num?` | `s` が数値ではない（`""` を含む） |
| `pop(xs)` | `T?` | リストが空 |
| `m[key]` | `T?` | キーが存在しない |
| `env(name)` | `str?` | 環境変数が設定されていない |

!!! note "この仕組みで防げるバグ"
    Lua 版の Lantern Night では、保存の中断によって 0 バイトのファイルが残りました。
    `lt.load_save` が `""`（Lua では真と判定される値）を返したため、`or "0"` による
    フォールバックは実行されず、`tonumber("")` が返した nil が原因で最初のフレームがクラッシュしました。
    Wick では、対応する式を `num(lt.load_save(k) ?? "") ?? 0` と書く必要があり、
    コンパイラが受け入れるのはこの形だけです。

## 代入の互換性 { #assignment-compatibility }

- `T?` が求められる場所には `T` を格納できます（型の拡大はそのまま行えます）。
- `T` が求められる場所には `T?` を格納**できません**。先にアンラップしてください。
- コンテナは不変です。`list<num>` が受け入れる要素は `num` のみ、
  `list<Prop>` が受け入れるのはそのレコード型のみです。
- `void`（戻り値の型がない関数）は、どこにも代入できません。
  void 関数の呼び出しは式ではなく文です。

## ハンドルの型は引き続き `num` { #handles-are-still-num }

現時点では、`lt.load_*` が返すメッシュ、テクスチャ、音声のハンドルは通常の `num` です。
テクスチャ ID を `lt.play` に渡しても型検査は通ります。不適切な使用は、実行時には
何も起こらないか、エラーになります。用途別のハンドル型は、ストア配信するゲームで必要になれば
候補になりますが、まだ採用されていません。

## ネイティブ 64 ビットのビルドと数値の精度 { #native-64-bit-builds-and-numeric-precision }

現在の [Lantern ソース](https://github.com/alikatgh/lantern/pull/5)では、Wick とエンジンの
既定のビルド先をネイティブ 64 ビットにしています。対応する 32 ビットのツールチェーンと
依存ライブラリを用意すれば、開発者は `-DWICK_HOST_BITS=32` を明示して選べます。
設定時とコンパイル時に、指定した幅と実際のターゲットの不一致を拒否します。
この指定自体がツールチェーンを提供したり、すべてのプラットフォームで 32 ビット版を保証したりするものではありません。
C++ から直接組み込む場合も同じ `WICK_HOST_BITS` 定義を使い、既定値は 64 です。

```sh
cmake -S . -B build -DWICK_HOST_BITS=64
cmake --build build
./build/lantern --build-info --json
```

build-info コマンドは、ウィンドウを開いたりゲームを実行したりせずに、コンパイル済みの
ホストのビット幅、選択したターゲット、アーキテクチャ、数値の保存幅と精度を返します。
現在のソースから利用する機能であり、以前の公開バイナリや保持している Nyurgun の
レビュー用アプリは置き換えていません。

Wick の `num` は引き続き C++ の `double` です。検証した binary64 ターゲットでは
保存幅が 64 ビット、整数の精度が 53 ビットです。ネイティブ 64 ビットのポインタを使っても、
正確な `i64`・`u64` 型の追加、既存のビット演算関数の変更、バイトコードのオペランド幅の拡大は行いません。
32 ビットを選んでも、ソース言語の数値の意味は同じです。
